# 1. Социальный кодинг

Социальный кодинг — это совместная работа над программным проектом, при которой участники видят историю изменений, обсуждают предлагаемые правки и объединяют результат контролируемым способом.

В обычной папке проекта непонятно:

- кто изменил файл;
- когда появилось изменение;
- зачем его сделали;
- как вернуться к предыдущему рабочему состоянию;
- как объединить работу нескольких участников.

Git решает задачу истории версий. GitHub добавляет удалённое хранение и инструменты командной работы.

### Три составляющие совместной работы

**История.** Команда видит автора, время и содержание каждого commit.

**Обсуждение.** Участники могут проверить diff и прокомментировать изменения до объединения.

**Open source.** Fork и Pull Request позволяют предлагать изменения в чужие проекты без прямого доступа на запись.

> **Комментарий преподавателю:** сравните Git с историей версий в Figma. В обоих случаях можно увидеть изменения и вернуться назад. Git дополнительно даёт ветки, локальную историю и обмен изменениями между участниками.

# 2. Git, GitHub и VS Code

Эти инструменты выполняют разные задачи.

## Git

Git — распределённая система контроля версий. Она хранит историю проекта и позволяет создавать независимые линии работы.

Большинство действий Git выполняет локально. Создать commit можно без интернета и без GitHub.

## GitHub

GitHub — сервис для удалённых Git-репозиториев. Он предоставляет:

- хранение репозитория в сети;
- управление доступом;
- Pull Requests;
- обсуждение изменений;
- Issues и другие инструменты совместной работы.

## Visual Studio Code

VS Code — редактор кода с графическим интерфейсом для Git. Раздел **Source Control** позволяет работать с репозиторием без постоянного ввода команд.

VS Code использует Git, установленный в операционной системе. Графический интерфейс и встроенный терминал работают с одним репозиторием. Действие, выполненное через интерфейс, сразу отражается в выводе `git status`, и наоборот.

> **Важно:** GitHub не требуется для локальных commits. Он понадобится, когда проект нужно опубликовать или синхронизировать с другими участниками.

Источник: [Source Control in VS Code](https://code.visualstudio.com/docs/sourcecontrol/overview)

# 3. Модели контроля версий

## Локальная модель

История находится на одном компьютере. Такой подход помогает вернуться к предыдущей версии, но плохо подходит для совместной работы. Поломка или потеря компьютера может привести к потере истории.

## Централизованная модель

Участники подключаются к общему серверу, на котором хранится основная история. Работа команды зависит от доступности этого сервера.

## Распределённая модель

Каждый `clone` содержит рабочие файлы и историю репозитория. Git относится к распределённым системам контроля версий.

У разработчика есть полноценная локальная история. Удалённый сервер нужен для обмена commits, резервного хранения и командной работы.

Источник: [Pro Git, Getting Started](https://git-scm.com/book/en/v2)

# 4. Четыре состояния работы с Git

Для понимания Git полезно разделить работу на четыре области.

## 4.1. Working tree

Рабочая папка проекта. Здесь находятся файлы, которые студент редактирует в VS Code: `index.html`, `styles.css`, изображения и документация.

Сохранение файла изменяет working tree, но не создаёт commit.

## 4.2. Staging area

Промежуточная область, в которой хранится выбранное содержимое следующего commit.

Staging area позволяет включить в commit только связанные изменения. Например, правки HTML можно зафиксировать отдельно от эксперимента с цветами в CSS.

## 4.3. Local repository

Локальная история commits. Git хранит её в каталоге `.git` внутри корня проекта.

Commit появляется сначала здесь. До выполнения push его нет на GitHub.

## 4.4. Remote repository

Удалённая версия репозитория на GitHub или другом сервере. Локальный и удалённый репозитории обмениваются commits через fetch, pull и push.

### Основная учебная модель

1. Сохранить файл.
2. Проверить diff.
3. Добавить нужные изменения в staging area.
4. Создать commit.
5. Отправить commit через push.

# 5. Структура репозитория

Пример веб-проекта:

```text
designer-profile/
├── index.html
├── styles.css
├── images/
├── README.md
├── .gitignore
└── .git/
```

Каталог `.git` содержит:

- конфигурацию репозитория;
- staging area, которую Git называет индексом;
- ссылки на ветки;
- журналы операций;
- объектное хранилище с историей.

Не удаляйте `.git` без причины. Рабочие файлы останутся на месте, но папка перестанет быть Git-репозиторием.

Git отслеживает файлы и их содержимое. Пустой каталог сам по себе в commit не попадёт. Если папка должна присутствовать в проекте, в неё обычно добавляют нужный файл или служебный `.gitkeep`.

# 6. Подготовка окружения

## 6.1. Установка

Понадобятся:

- [Visual Studio Code](https://code.visualstudio.com/);
- [Git](https://git-scm.com/);
- аккаунт GitHub для публикации проекта.

Проверка Git во встроенном терминале VS Code:

```bash
git --version
```

## 6.2. Настройка автора commits

```bash
git config --global user.name "Имя Фамилия"
git config --global user.email "student@example.com"
```

Имя и email записываются в commit и описывают его автора. Они не являются логином или паролем.

Проверка настроек:

```bash
git config --global --list
```

## 6.3. Авторизация GitHub

VS Code предложит войти в GitHub при публикации проекта, клонировании закрытого репозитория или выполнении push без действующей авторизации.

## 6.4. Открытие проекта

Используйте **File > Open Folder** и выбирайте корень проекта. Source Control работает с репозиторием открытой папки.

Доверяйте только знакомым проектам. VS Code может запускать задачи, расширения и другие настройки из рабочей папки.

Источник: [VS Code Source Control Quickstart](https://code.visualstudio.com/docs/sourcecontrol/quickstart)

# 7. Панель Source Control

Панель открывается кнопкой Source Control на боковой панели или сочетанием `Ctrl+Shift+G`. На macOS VS Code использует `Control+Shift+G`.

## Changes

Список изменений, которые ещё не добавлены в staging area.

## Staged Changes

Содержимое, подготовленное для следующего commit.

## Diff editor

Сравнение исходной и изменённой версии файла. Diff показывает добавленные, удалённые и изменённые строки.

## Source Control Graph

Граф истории, веток, входящих и исходящих commits.

> **Демонстрация:** измените одну строку в `index.html`, сохраните файл и откройте его в разделе Changes. Обратите внимание студентов на точное различие между старой и новой строкой.

Источник: [Source Control in VS Code](https://code.visualstudio.com/docs/sourcecontrol/overview)

# 8. Рабочий цикл в VS Code

## Шаг 1. Save

Сохраните файл на диске. Git увидит изменение, но не создаст commit автоматически.

## Шаг 2. Review

Откройте diff и проверьте:

- относится ли изменение к текущей задаче;
- нет ли случайно удалённых строк;
- не попали ли в файл пароль, токен или временные данные;
- соответствует ли код ожидаемому результату.

## Шаг 3. Stage

Выберите файлы или отдельные строки, которые должны войти в следующий commit.

## Шаг 4. Commit

Создайте локальную контрольную точку с коротким сообщением.

## Шаг 5. Push

Отправьте созданные commits в удалённый репозиторий.

Источник: [Staging and committing changes](https://code.visualstudio.com/docs/sourcecontrol/staging-commits)

# 9. Создание нового репозитория

## Через интерфейс VS Code

1. Откройте папку проекта через **File > Open Folder**.
2. Перейдите в Source Control.
3. Нажмите **Initialize Repository**.

Альтернативный путь:

1. Откройте Command Palette.
2. Выполните **Git: Initialize Repository**.

## Через терминал

```bash
git init
```

После инициализации появляется каталог `.git`. Репозиторий пока остаётся локальным. GitHub-репозиторий ещё не создан, и файлы никуда не отправлены.

# 10. Клонирование существующего репозитория

## Через VS Code

1. Откройте Source Control.
2. Нажмите **Clone Repository**.
3. Вставьте URL репозитория или выберите **Clone from GitHub**.
4. Укажите локальную папку.
5. Откройте созданный clone в новом окне VS Code.

То же действие через Command Palette: **Git: Clone**.

## Через терминал

```bash
git clone https://github.com/user/project.git
```

Clone переносит рабочие файлы, историю и информацию о ветках. Скачивание ZIP переносит только текущее содержимое файлов.

Clone не выдаёт право на push. Права определяет владелец удалённого репозитория.

Источник: [Working with repositories and remotes](https://code.visualstudio.com/docs/sourcecontrol/repos-remotes)

# 11. Статусы файлов и diff

VS Code показывает короткие обозначения рядом с файлами.

| Статус | Значение |
|---|---|
| `U` | Untracked. Новый файл ещё не включён в историю Git |
| `M` | Modified. Отслеживаемый файл изменён |
| `D` | Deleted. Отслеживаемый файл удалён |

Щёлкните файл в Changes, чтобы открыть diff.

Проверка в терминале:

```bash
git status
```

`git status` помогает разобраться, когда интерфейс кажется непонятным. Команда показывает текущую ветку, staged и unstaged изменения, а также состояние синхронизации.

# 12. Staging area

## Stage одного файла

Нажмите `+` рядом с файлом в Changes.

Команда:

```bash
git add index.html
```

## Stage всех проверенных файлов

Нажмите `+` в заголовке Changes.

Команда:

```bash
git add .
```

Перед `git add .` проверьте список изменений. Команда добавляет все подходящие изменения внутри текущей папки.

## Stage выбранных строк

VS Code позволяет выделить диапазон в diff и подготовить только эти строки. Такой подход помогает разделить несвязанные правки на отдельные commits.

## Unstage

Нажмите `-` рядом с файлом в Staged Changes.

Unstage убирает изменения из следующего commit, но сохраняет их в рабочем файле.

> **Ключевая идея:** staging хранит выбранное содержимое файла в конкретный момент. Если после stage снова изменить файл, он может одновременно появиться в Staged Changes и Changes.

# 13. Commit

Commit — локальная контрольная точка проекта.

Порядок действий в VS Code:

1. Проверьте Staged Changes.
2. Введите короткое сообщение.
3. Нажмите **Commit**.

Пример сообщения:

```text
Add portfolio gallery
```

Команда:

```bash
git commit -m "Add portfolio gallery"
```

Хорошее сообщение описывает результат изменения. Оно помогает понять историю без открытия каждого diff.

Примеры:

- `Create page structure`
- `Add base typography`
- `Fix mobile navigation`
- `Update portfolio images`

Commit остаётся локальным до выполнения push.

> **Методический совет:** на занятии выполняйте stage явно. Если ничего не staged, поведение кнопки Commit может зависеть от настроек VS Code.

# 14. Remote и публикация на GitHub

Remote — ссылка локального репозитория на удалённый.

`origin` — обычное имя первого remote.

## Publish to GitHub

Команда **Publish to GitHub** выполняет несколько действий:

1. создаёт репозиторий на GitHub;
2. добавляет его как remote;
3. отправляет локальные commits.

При публикации можно выбрать public или private repository.

## Подключение существующего удалённого репозитория

В VS Code откройте **More Actions > Remotes > Add Remote**.

Команда:

```bash
git remote add origin https://github.com/user/project.git
```

Проверка:

```bash
git remote -v
```

Не путайте remote и ветку:

- `origin` обычно обозначает удалённый репозиторий;
- `main` или `master` обычно обозначает ветку.

# 15. Fetch, Pull, Push и Sync Changes

## Fetch

Получает сведения и commits из remote, но не изменяет текущую локальную ветку.

```bash
git fetch
```

Fetch удобно использовать перед просмотром входящих изменений.

## Pull

Получает удалённые commits и интегрирует их в текущую ветку.

```bash
git pull
```

Pull может привести к конфликту, если локальные и удалённые изменения затрагивают одни и те же строки.

## Push

Отправляет локальные commits в удалённую ветку.

```bash
git push
```

## Sync Changes

VS Code сначала выполняет pull, затем push. Sync удобно использовать, когда нужно получить чужие commits и отправить свои.

Если pull остановился на конфликте, VS Code не перейдёт к push. Сначала нужно разрешить конфликт и завершить операцию.

Источник: [Working with repositories and remotes](https://code.visualstudio.com/docs/sourcecontrol/repos-remotes)

# 16. Ветки

Ветка — отдельная линия работы. Она позволяет разрабатывать изменение, не вмешиваясь в стабильное состояние основной ветки.

Пример:

```text
main
└── feature/hero-section
```

`main` содержит стабильную страницу. В `feature/hero-section` студент меняет hero-блок.

## Создание ветки в VS Code

1. Нажмите имя текущей ветки в строке состояния.
2. Выберите **Create new branch**.
3. Введите имя, например `feature/hero-section`.

Через Command Palette можно выполнить **Git: Create Branch**.

## Переключение ветки

Нажмите имя ветки в строке состояния или выполните **Git: Switch Branch**.

Современные команды терминала:

```bash
git switch feature/hero-section
```

Создание и переключение:

```bash
git switch -c feature/hero-section
```

Перед переключением проверьте незавершённые изменения. Git может потребовать commit, stash или другое решение, если правки мешают безопасной смене ветки.

Источники: [Branches and worktrees in VS Code](https://code.visualstudio.com/docs/sourcecontrol/branches-worktrees), [git-switch](https://git-scm.com/docs/git-switch)

# 17. Merge

Merge объединяет изменения выбранной ветки с текущей.

Пример объединения `feature/hero-section` в `main`:

1. Переключитесь на `main`.
2. Откройте Command Palette.
3. Выполните **Git: Merge Branch**.
4. Выберите `feature/hero-section`.
5. Проверьте diff и откройте страницу в браузере.
6. Выполните push, чтобы опубликовать результат.

Команды:

```bash
git switch main
git merge feature/hero-section
git push
```

> **Главное правило:** merge вливает выбранную ветку в текущую. Перед операцией всегда проверяйте имя текущей ветки.

# 18. Конфликт слияния

Конфликт возникает, когда Git не может автоматически выбрать итоговое содержимое.

Например, в одной ветке записано:

```css
color: blue;
```

В другой ветке та же строка выглядит так:

```css
color: red;
```

VS Code предлагает inline actions или трёхсторонний Merge Editor:

- **Current** — содержимое текущей ветки;
- **Incoming** — входящее изменение;
- **Result** — итоговый файл.

Порядок разрешения конфликта:

1. Откройте конфликтный файл.
2. Сравните Current и Incoming.
3. Выберите нужный вариант или отредактируйте Result вручную.
4. Проверьте итоговый код.
5. Добавьте файл в staging area.
6. Завершите merge commit.

**Accept Both Changes** не гарантирует корректный результат. Два фрагмента могут противоречить друг другу или нарушить синтаксис.

Источник: [Resolve merge conflicts in VS Code](https://code.visualstudio.com/docs/sourcecontrol/merge-conflicts)

# 19. Stash

Stash временно откладывает незавершённые изменения и очищает рабочую папку.

Пример ситуации: студент меняет дизайн в feature-ветке, но должен срочно переключиться на `main` и исправить ошибку.

## Сохранение

В VS Code откройте **More Actions > Stash** или выполните **Git: Stash** через Command Palette.

Команда:

```bash
git stash
```

## Возврат изменений

```bash
git stash apply
```

`apply` возвращает изменения и сохраняет запись stash. `pop` возвращает изменения и удаляет запись при успешном применении.

Перед восстановлением stash проверьте текущую ветку. Возврат изменений тоже может вызвать конфликт.

Stash помогает прерваться, но не заменяет понятную историю commits.

# 20. История в VS Code

## Source Control Graph

Показывает commits, ветки, их объединения, входящие и исходящие изменения.

## Timeline

Показывает историю Git и локальных сохранений выбранного файла.

## Git blame

Показывает автора и commit для конкретной строки. Blame полезен, когда нужно найти контекст изменения, а не назначить виноватого.

История помогает ответить на вопросы:

- что изменилось;
- кто изменил;
- когда появилось изменение;
- почему его сделали;
- в каком commit находится рабочая версия.

> **Демонстрация:** откройте один commit в Graph, затем выберите строку файла и покажите её историю.

# 21. Clone и Fork

## Clone

Создаёт локальную копию репозитория с историей. Clone не создаёт новый репозиторий в аккаунте GitHub.

## Fork

Создаёт связанную копию чужого репозитория в вашем аккаунте GitHub.

Fork используют, когда участник не может отправлять commits прямо в исходный репозиторий.

Типичный процесс работы с открытым проектом:

1. Создать fork на GitHub.
2. Выполнить clone своей копии.
3. Создать отдельную ветку.
4. Внести изменения и выполнить push.
5. Открыть Pull Request в исходный проект.

# 22. Pull Request

Pull Request предлагает объединить изменения одной ветки с другой и создаёт место для проверки и обсуждения.

## Процесс

1. Создайте тематическую ветку.
2. Выполните commits.
3. Отправьте ветку через Push или Publish Branch.
4. Откройте Pull Request.
5. Проверьте diff.
6. Обсудите изменения.
7. Исправьте замечания новыми commits.
8. Выполните merge после проверки.
9. Обновите локальный `main` через pull.

Базовые Git-операции и авторизация GitHub встроены в VS Code. Для управления Pull Requests и Issues внутри редактора установите расширение **GitHub Pull Requests and Issues**. Альтернативный вариант — открыть Pull Request на сайте GitHub.

Источник: [Working with GitHub in VS Code](https://code.visualstudio.com/docs/sourcecontrol/github)

# 23. `.gitignore` для веб-проекта

`.gitignore` содержит правила файлов и каталогов, которые Git не должен добавлять в репозиторий.

## Обычно хранят в Git

- HTML;
- CSS;
- JavaScript;
- `README.md`;
- SVG;
- оптимизированные изображения проекта;
- конфигурацию сборки, если она нужна проекту.

## Обычно исключают

- `.DS_Store`;
- `.env` и секреты;
- `node_modules/`;
- временные экспорты;
- локальные кеши;
- крупные PSD, видео и архивы, если проект не требует их версионирования.

Пример:

```gitignore
.DS_Store
.env
node_modules/
*.tmp
*.zip
```

Не добавляйте токены и пароли. Если секрет уже опубликован, одного удаления из нового commit недостаточно. Секрет нужно отозвать и заменить.

# 25. Исправления к старому конспекту

## Remote обычно называется `origin`

Некорректный пример:

```bash
git remote add master https://github.com/user/project.git
```

Более привычный вариант:

```bash
git remote add origin https://github.com/user/project.git
```

`master` и `main` обычно обозначают ветки.

## `git commit -am` не добавляет новые файлы

Команда:

```bash
git commit -am "Update layout"
```

Флаг `-a` добавляет изменения и удаления уже отслеживаемых файлов. Новый untracked-файл сначала нужно добавить через `git add`.

## Sync Changes выполняет pull и push

Sync Changes нельзя считать одной заменой для любых удалённых операций. VS Code сначала получает и интегрирует изменения, затем отправляет локальные commits.

## Для переключения веток удобнее `git switch`

`git checkout` остаётся доступным, но выполняет несколько разных задач. Для обучения переключению веток понятнее использовать `git switch`.

Источники: [VS Code remotes](https://code.visualstudio.com/docs/sourcecontrol/repos-remotes), [git-commit](https://git-scm.com/docs/git-commit), [git-switch](https://git-scm.com/docs/git-switch)

# 29. Типичные ошибки

## Commit создан, но на GitHub ничего нет

Commit находится в локальном репозитории. Выполните push.

## Push rejected

Удалённая ветка содержит commits, которых нет локально. Выполните Fetch, изучите входящие изменения и синхронизируйте историю.

Не используйте force push вслепую. Он может перезаписать удалённую историю и удалить чужие commits.

## Файл не попал в commit

Проверьте, находился ли файл в Staged Changes перед commit.

## Случайно нажат Discard Changes

Discard может удалить незакоммиченную работу. Перед удалением изменений определите, что требуется:

- Unstage, если файл нужно убрать только из следующего commit;
- Stash, если работу нужно временно отложить;
- Commit, если изменение уже готово.

## Непонятное состояние репозитория

Откройте терминал и выполните:

```bash
git status
```

Прочитайте сообщение Git полностью. Обычно оно сообщает, есть ли конфликт, незавершённый merge, staged изменения или расхождение с remote.

# 30. Проверка понимания

Сначала задайте вопросы группе, затем откройте ответы.

## 1. Что находится в Staged Changes?

Точное содержимое следующего commit.

## 2. Где хранится commit до push?

В локальном репозитории.

## 3. Что делает Sync Changes?

Сначала выполняет pull, затем push.

## 4. Чем Fork отличается от Clone?

Fork создаёт копию репозитория в аккаунте GitHub. Clone создаёт локальную копию репозитория с историей.

## 5. Почему сохранение файла не равно commit?

Сохранение изменяет working tree. Commit создаёт запись в локальной истории из содержимого staging area.

## 6. Зачем перед commit читать diff?

Чтобы заметить случайные изменения, проверить содержание commit и не опубликовать лишние данные.

# 32. Итоги

| Понятие | Что означает |
|---|---|
| Repository | Файлы проекта и история Git |
| Working tree | Текущее содержимое рабочей папки |
| Stage | Выбранное содержимое следующего commit |
| Commit | Локальная контрольная точка |
| Branch | Отдельная линия работы |
| Remote | Связанный удалённый репозиторий |
| Push | Отправка локальных commits в remote |
| Pull | Получение и интеграция удалённых commits |
| Pull Request | Проверка и обсуждение изменений до merge |

Главная последовательность работы:

```text
Save → Review diff → Stage → Commit → Push
```

Для командной задачи добавляются ветка и Pull Request:

```text
Create branch → Make changes → Commit → Push → Pull Request → Merge
```
